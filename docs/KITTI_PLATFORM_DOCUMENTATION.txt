1. PRODUCT OVERVIEW
================================================================================

Kitti is a real-time multiplayer 9-card game (similar to Teen Patti) where 2–5
players compete by arranging 9 dealt cards into 3 sets of 3 cards each and
submitting them for evaluation.

TECH STACK
  Frontend   : Next.js 14 (App Router, TypeScript, Tailwind CSS)
  Real-Time  : Node.js + Socket.IO v4
  Game Logic : FastAPI (Python 3.12)
  Database   : PostgreSQL 16
  Cache/State: Redis 7
  Auth       : JWT + OTP (phone/email)
  Container  : Docker + Docker Compose

KEY FEATURES
  - Real-time multiplayer rooms (2–5 players)
  - Server-side card dealing and hand evaluation (anti-cheat)
  - Virtual coin wallet with entry fees and rewards
  - OTP-based authentication (phone/email)
  - Leaderboard with win/earnings stats
  - Mobile-first responsive UI with felt-table aesthetic

  ┌──────────────────┐  ┌────────────────────────┐
  │  Node.js (:4000) │  │  FastAPI (:8000)        │
  │  Socket.IO Engine│  │  Auth, Wallet,          │
  │  Room/Game Mgmt  │  │  Game Logic, Leaderboard│
  └──────┬───────────┘  └──────────┬─────────────┘
         │ HTTP (internal)         │
         │◄────────────────────────┘
         │
  ┌──────▼─────────┐     ┌───────────────────────┐
  │  Redis (:6379) │     │  PostgreSQL (:5432)    │
  │  Game State    │     │  Users, Matches,       │
  │  Room State    │     │  Transactions, OTP     │
  └────────────────┘     └───────────────────────┘

DATA FLOW
  1. Player authenticates via FastAPI → gets JWT
  2. Frontend connects to Node.js Socket.IO with JWT
  3. Node.js validates JWT in middleware
  4. Room/game events flow through Node.js ↔ Redis
  5. Game evaluation calls Node.js → FastAPI (internal HTTP)
  6. Match results + wallet updates written to PostgreSQL via FastAPI
  7. Real-time updates broadcast from Node.js to all room members

4. DATABASE SCHEMA
================================================================================

TABLE: users
  id            UUID         PK
  username      VARCHAR(50)  UNIQUE NOT NULL
  email         VARCHAR(255) UNIQUE
  phone         VARCHAR(20)  UNIQUE
  password_hash VARCHAR(255)
  coins         BIGINT       DEFAULT 1000 (welcome bonus)
  is_active     BOOLEAN      DEFAULT TRUE
  is_verified   BOOLEAN      DEFAULT FALSE
  total_games   INTEGER      DEFAULT 0
  total_wins    INTEGER      DEFAULT 0
  total_earnings BIGINT      DEFAULT 0
  created_at    TIMESTAMPTZ
  updated_at    TIMESTAMPTZ
  last_seen_at  TIMESTAMPTZ

  CONSTRAINT: email IS NOT NULL OR phone IS NOT NULL

TABLE: rooms
  id          VARCHAR(8)   PK (short code e.g. "A3F9B2C1")
  host_id     UUID         FK → users
  status      ENUM         (waiting|playing|finished|cancelled)
  max_players INTEGER      CHECK 2–5
  entry_fee   INTEGER      DEFAULT 100
  options     JSONB        { "enable235Rule": boolean }
  created_at  TIMESTAMPTZ
  closed_at   TIMESTAMPTZ

TABLE: matches
  id           UUID        PK
  room_id      VARCHAR(8)  FK → rooms
  winner_id    UUID        FK → users (NULL = tie)
  status       ENUM        (in_progress|complete|cancelled)
  total_pot    INTEGER
  is_tie       BOOLEAN     DEFAULT FALSE
  result_data  JSONB       (full result snapshot for auditing)
  started_at   TIMESTAMPTZ
  completed_at TIMESTAMPTZ

TABLE: match_players
  id           UUID    PK
  match_id     UUID    FK → matches
  user_id      UUID    FK → users
  sets_won     INTEGER CHECK 0–3
  is_winner    BOOLEAN
  coins_earned INTEGER
  coins_lost   INTEGER
  UNIQUE (match_id, user_id)

TABLE: transactions
  id             UUID            PK
  user_id        UUID            FK → users
  match_id       UUID            FK → matches (nullable)
  amount         INTEGER         CHECK > 0
  type           ENUM            (credit|debit|refund)
  description    VARCHAR(255)
  balance_before BIGINT
  balance_after  BIGINT
  created_at     TIMESTAMPTZ

TABLE: otp_codes
  id         UUID
  target     VARCHAR(255)  (phone or email)
  code       VARCHAR(6)
  is_used    BOOLEAN       DEFAULT FALSE
  expires_at TIMESTAMPTZ
  created_at TIMESTAMPTZ

5. REDIS DESIGN
================================================================================

KEY PATTERNS
  room:{roomId}                     → Full room state JSON (TTL: 2 hours)
  game:{gameId}                     → Full game state JSON (TTL: 2 hours)
  game:{gameId}:cards:{userId}      → Player's private 9 cards (TTL: 2 hours)
  disconnect:{roomId}:{userId}      → Disconnect grace tracking (TTL: 5 min)
  ratelimit:connect:{userId}        → Rate limit counter (TTL: 60s window)

ROOM STATE SCHEMA (JSON)
  {
    roomId:       string,
    hostId:       string,
    status:       "waiting" | "playing" | "finished",
    maxPlayers:   number,
    entryFee:     number,
    options:      { enable235Rule: boolean },
    players:      [{ userId, username, isReady, isConnected }],
    currentGameId: string | null,
    createdAt:    timestamp
  }

GAME STATE SCHEMA (JSON)
  {
    gameId:         string,
    roomId:         string,
    status:         "dealing" | "submitting" | "evaluating" | "complete",
    players:        [{ userId, username, hasSubmitted, submittedAt, sets? }],
    options:        { enable235Rule: boolean },
    entryFee:       number,
    totalPot:       number,
    startedAt:      timestamp,
    submitDeadline: timestamp,
    result:         { ... } | null
  }

PLAYER CARDS (Private — never shared)
  [
    { id, suit, value, displayValue, display },  // × 9
    ...
  ]

SECURITY NOTE: Player cards are stored per-userId under a game-scoped key.
Cards are only ever sent via targeted socket.emit() to the owning player.
They are never included in the shared game state.

8. GAME RULES & LOGIC
================================================================================

THE GAME
  - A standard 52-card deck is shuffled server-side
  - Each player receives 9 cards (dealt face-down, private)
  - Players arrange their 9 cards into 3 sets of 3 cards each
  - Each set is evaluated as a 3-card poker hand
  - The player who wins the most sets wins the match

HAND RANKINGS (highest to lowest)
  6 — Trail (Three of a Kind)      e.g. A-A-A, K-K-K
  5 — Pure Sequence (Straight Flush) e.g. A♠-K♠-Q♠
  4 — Sequence (Straight)          e.g. A-K-Q, 5-4-3 (mixed suits)
  3 — Flush (Color)                e.g. K♥-9♥-3♥
  2 — Pair                         e.g. Q-Q-7
  1 — High Card                    e.g. A-K-9

TIEBREAKER RULES
  Same rank:     Compare card values in descending order
  Trail:         Higher triple wins (A-A-A > K-K-K)
  Pure/Sequence: Higher top card wins
  Flush:         Compare all 3 cards high-to-low
  Pair:          Higher pair wins; kicker if pair ties
  High Card:     Compare all 3 cards high-to-low

SPECIAL RULES
  A-2-3:         Valid sequence (Ace plays low)
  A-K-Q:         Valid sequence (Ace plays high)
  2-3-5 Rule:    Optional — makes 2-3-5 the highest possible sequence
                 (must be enabled at room creation)

CARD VALUES
  Ace=14, King=13, Queen=12, Jack=11, 10–2 as face value

WINNING
  Player who wins 2 out of 3 sets wins the match
  If sets won are equal (1-1 on 2 players, or multi-way tie), it's a draw
  Winner takes the entire pot (all entry fees)
  Tie: pot is not distributed (house keeps, or refund option)

SUBMISSION
  Players have 60 seconds to arrange and submit their sets
  Players who don't submit are removed from evaluation
  If fewer than 2 players submit, game is cancelled and refunded

9. ANTI-CHEAT DESIGN
================================================================================

ALL GAME LOGIC IS SERVER-SIDE

1. Card Dealing
   - Deck built and shuffled by Node.js server (Fisher-Yates)
   - Each player's 9 cards stored privately in Redis: game:{id}:cards:{userId}
   - Cards are ONLY sent to the player who owns them via targeted socket.emit
   - Other players' cards are never included in any broadcast

2. Set Submission Validation
   Server validates EVERY submission before accepting:
   ✓ Exactly 3 sets submitted
   ✓ Each set has exactly 3 cards
   ✓ All 9 submitted card IDs match the dealt cards exactly
   ✓ No duplicate card IDs across sets
   ✓ Submission is within the deadline
   ✓ Player hasn't already submitted
   Any validation failure returns an error and logs the attempt

3. Hand Evaluation
   - Done server-side by the evaluator module
   - Client-side evaluation is display-only (hand hints in UI)
   - Server result is authoritative

4. State Isolation
   - Game state in Redis never includes other players' hands
   - sanitizeGameState() strips opponents' set data before sending to clients

5. Wallet
   - All coin mutations happen atomically in PostgreSQL
   - Only FastAPI modifies coin balances (never the client)
   - Every transaction logged with balance_before and balance_after

10. WALLET SYSTEM
================================================================================

MVP VIRTUAL COINS
  - New users receive 1000 coins on registration
  - Entry fee: 100 coins per game (configurable via GAME_ENTRY_FEE env var)
  - Winner receives: entryFee × playerCount coins
  - All balances stored in PostgreSQL users.coins (BIGINT, minimum 0)

TRANSACTION FLOW
  1. Player creates or joins room → Node.js calls POST /api/wallet/transaction
     { user_id, amount: 100, type: "debit", description: "Game entry fee" }
  2. FastAPI validates balance, deducts coins, records transaction
  3. After game: winner credited with full pot
  4. All transactions include balance_before / balance_after for auditing

COIN ACQUISITION (Future)
  - In-app purchase (Stripe/Razorpay integration point)
  - Daily login bonus
  - Referral rewards

12. LOCAL DEVELOPMENT SETUP
================================================================================

PREREQUISITES
  - Node.js 20+
  - Python 3.12+
  - PostgreSQL 16
  - Redis 7
  - Docker (optional but recommended)

STEP 1: Clone and set up environment files

  cp node-server/.env.example node-server/.env
  cp fastapi-service/.env.example fastapi-service/.env
  cp frontend/.env.example frontend/.env.local

  Edit each .env file and set JWT_SECRET and INTERNAL_API_KEY to matching values.

STEP 2: Start PostgreSQL and Redis

  Option A — Docker:
    docker run -d --name kitti-pg -e POSTGRES_DB=kitti_db \
      -e POSTGRES_USER=kitti -e POSTGRES_PASSWORD=kitti_pass \
      -p 5432:5432 postgres:16-alpine

    docker run -d --name kitti-redis -p 6379:6379 redis:7-alpine

  Option B — Local installation (macOS):
    brew services start postgresql@16
    brew services start redis

STEP 3: Create database schema

  psql -U kitti -d kitti_db -f database/schema.sql

STEP 4: Start FastAPI

  cd fastapi-service
  python -m venv venv
  source venv/bin/activate     # Windows: venv\Scripts\activate
  pip install -r requirements.txt
  uvicorn app.main:app --reload --port 8000

STEP 5: Start Node.js server

  cd node-server
  npm install
  npm run dev

STEP 6: Start Next.js frontend

  cd frontend
  npm install
  npm run dev

  Open http://localhost:3000

TESTING THE FULL FLOW
  1. Open http://localhost:3000 in two browser windows
  2. Login with phone: +1234567890 (OTP shown in FastAPI console)
  3. Create a room in window 1
  4. Join with room code in window 2
  5. Start the game from window 1 (host)
  6. Arrange cards in both windows and submit
  7. Results page shows winner

16. NGINX REVERSE PROXY CONFIG
================================================================================

Save as /etc/nginx/sites-available/kitti:

  server {
      listen 80;
      server_name yourdomain.com www.yourdomain.com;

      # Redirect HTTP → HTTPS
      return 301 https://$server_name$request_uri;
  }

  server {
      listen 443 ssl http2;
      server_name yourdomain.com;

      ssl_certificate     /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
      ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;

      # Security headers
      add_header X-Frame-Options DENY;
      add_header X-Content-Type-Options nosniff;
      add_header Strict-Transport-Security "max-age=31536000" always;

      # ── Next.js Frontend ────────────────────────────────────────────────────
      location / {
          proxy_pass http://127.0.0.1:3000;
          proxy_http_version 1.1;
          proxy_set_header Upgrade $http_upgrade;
          proxy_set_header Connection 'upgrade';
          proxy_set_header Host $host;
          proxy_cache_bypass $http_upgrade;
      }

      # ── Socket.IO (Node.js) ─────────────────────────────────────────────────
      location /socket.io/ {
          proxy_pass http://127.0.0.1:4000;
          proxy_http_version 1.1;
          proxy_set_header Upgrade $http_upgrade;
          proxy_set_header Connection "upgrade";
          proxy_set_header Host $host;
          proxy_set_header X-Real-IP $remote_addr;
          proxy_read_timeout 3600s;
          proxy_send_timeout 3600s;
      }

      # ── FastAPI REST ─────────────────────────────────────────────────────────
      location /api/ {
          proxy_pass http://127.0.0.1:8000;
          proxy_set_header Host $host;
          proxy_set_header X-Real-IP $remote_addr;
          proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      }
  }

Enable and reload:
  sudo ln -s /etc/nginx/sites-available/kitti /etc/nginx/sites-enabled/
  sudo nginx -t
  sudo systemctl reload nginx

SSL with Certbot:
  sudo apt install -y certbot python3-certbot-nginx
  sudo certbot --nginx -d yourdomain.com -d www.yourdomain.com

17. SCALING STRATEGY
================================================================================

CURRENT (MVP — Single Server)
  All services on one VPS. Sufficient for ~100 concurrent players.

PHASE 2 — HORIZONTAL SCALING (1K+ players)

  Node.js Horizontal Scaling:
  - Add @socket.io/redis-adapter to share socket rooms across Node.js instances
  - Run N Node.js instances (one per CPU core)
  - Nginx upstream load balances with sticky sessions:
      upstream kitti_socketio {
          ip_hash;
          server 127.0.0.1:4001;
          server 127.0.0.1:4002;
          server 127.0.0.1:4003;
      }

  FastAPI Scaling:
  - Increase uvicorn --workers to match CPU cores
  - Or deploy with Gunicorn + uvicorn workers:
      gunicorn app.main:app -k uvicorn.workers.UvicornWorker -w 4

  Database Scaling:
  - Read replicas for leaderboard and history queries
  - Connection pooling via PgBouncer (transaction mode)
  - Partition transactions table by month if >10M rows

  Redis Scaling:
  - Redis Sentinel for HA (automatic failover)
  - Redis Cluster for data sharding at very high scale

PHASE 3 — MICROSERVICES (10K+ players)
  - Separate game rooms into their own service
  - Event-driven architecture with Kafka/RabbitMQ
  - CDN for frontend (Cloudflare / Vercel)
  - Kubernetes for container orchestration
  - Separate read/write databases

ESTIMATED CAPACITY PER VPS TIER
  2 vCPU, 4GB RAM  → ~100 concurrent players, 20 active games
  4 vCPU, 8GB RAM  → ~500 concurrent players, 100 active games
  8 vCPU, 16GB RAM → ~2000 concurrent players, 400 active games

18. SECURITY HARDENING
================================================================================

AUTHENTICATION
  ✓ JWT secret: minimum 64 random characters
  ✓ Tokens expire after 24 hours (configurable)
  ✓ OTP codes expire after 10 minutes
  ✓ Used OTPs immediately invalidated in DB
  ✓ Rate limiting on socket connections (10/min per user)

ANTI-CHEAT
  ✓ All card logic server-side
  ✓ Player cards never broadcast to room (only private emit)
  ✓ Every set submission validated against Redis-stored dealt cards
  ✓ Move timestamps validated against deadline

NETWORK
  ✓ HTTPS enforced via Nginx + Certbot
  ✓ Internal services only exposed on 127.0.0.1
  ✓ INTERNAL_API_KEY protects Node → FastAPI calls
  ✓ CORS restricted to known frontend origin
  ✓ Firewall: only ports 80, 443, 22 public

DATABASE
  ✓ Parameterized queries (SQLAlchemy ORM — no raw SQL)
  ✓ Minimum privilege DB user
  ✓ Connection pooling with max limits

PRODUCTION CHECKLIST
  [ ] Change all default passwords in .env
  [ ] Set NODE_ENV=production
  [ ] Remove dev_otp from OTP endpoint response
  [ ] Disable /docs and /redoc endpoints
  [ ] Enable PostgreSQL SSL connections

  [ ] Enable UFW firewall:
